## Current State Analysis

### 1) 两个 JSON 文件的关键差异

- 两个文件的顶层结构一致：`{ v, id, name, createdAt, updatedAt, snapshot }`，且 snapshot 结构一致：`{ v, capturedAt, fields, memory }`。
- **核心差异在 snapshot.memory.roofBackground：**
  - 601e... 中 roofBackground 为空或很小（文件体积较小）。
  - 403c... 中 roofBackground 为超长 `data:image/...;base64,...`（文件体积极大）。
- 这类“大字段”在 GitHub 保存后，读取时如果走 GitHub Contents API（`/repos/:owner/:repo/contents/:path`）会触发其 **1MB 左右返回限制**：API 可能不返回 `content`（或返回截断），导致当前 `getFile()` 解码得到空字符串/不完整字符串，进而 JSON.parse 失败或 snapshot 不完整，表现为“无法加载/加载不完整”。

  - 仅从 `data.content` 解码；当 `data.content` 缺失/截断时没有 fallback。

## Proposed Changes

### A) 让所有报价（含大 base64 图片）稳定加载：为 getFile 增加 raw/download_url fallback

修改文件：
- [github-sync/githubApi.js](file:///Users/jqz/Library/CloudStorage/OneDrive-%E4%B8%AA%E4%BA%BA/Github%20Project/minova/github-sync/githubApi.js)
- [github-sync/repoStore.js](file:///Users/jqz/Library/CloudStorage/OneDrive-%E4%B8%AA%E4%BA%BA/Github%20Project/minova/github-sync/repoStore.js)
- （可选但建议同步）[index.html](file:///Users/jqz/Library/CloudStorage/OneDrive-%E4%B8%AA%E4%BA%BA/Github%20Project/minova/index.html#L2665-L2671) 内联的 createRepoStore.getFile

具体做法：
1. 在 `createGitHubApi` 返回对象中新增一个“可请求任意 URL”的方法（命名建议 `fetchUrl(url, init)`）：
   - 复用内部 `request(url, init, attempt)`，以便自动携带 Authorization token、限流、重试等能力。
2. 在 `repoStore.getFile()` 中读取 contents API 的返回 `data` 后：
   - 若 `data.content` 存在：保持现状（base64 解码）。
   - 若 `data.content` 不存在但 `data.download_url` 存在：
     - 调用 `api.fetchUrl(data.download_url, { method: 'GET' })` 获取完整文本；
     - 将返回的 string 作为 `content` 返回（并保留 sha/raw）。
3. 错误处理：
   - 如果 download_url 拉取失败：保持抛错（让上层 toast “加载失败”），并在控制台输出错误信息。

预期效果：
- 大文件仍可以通过 raw 方式拉取完整内容，避免 contents API 的 1MB 限制。
- 不需要改变报价 JSON 的 schema，也不需要迁移历史报价文件。

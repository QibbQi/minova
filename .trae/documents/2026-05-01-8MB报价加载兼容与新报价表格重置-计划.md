## Current State Analysis

### 1) 8MB 加载失败的根因（已可在本地样本复现）

- 对比根目录两个报价快照文件：
  - [601e55cc-36ba-47f8-b950-c9111eafe683.json](file:///Users/jqz/Library/CloudStorage/OneDrive-%E4%B8%AA%E4%BA%BA/Github%20Project/minova/601e55cc-36ba-47f8-b950-c9111eafe683.json)
  - [403c4ff2-a4fb-4a75-a9bf-e293baeaa5bb.json](file:///Users/jqz/Library/CloudStorage/OneDrive-%E4%B8%AA%E4%BA%BA/Github%20Project/minova/403c4ff2-a4fb-4a75-a9bf-e293baeaa5bb.json)
- 两者 schema 一致；关键差别是 `snapshot.memory.roofBackground`：
  - 小文件（601e...）：roofBackground 小/为空。
  - 大文件（403c...）：roofBackground 为超长 base64 dataURL（导致单文件体积极大）。
- GitHub 的 Contents API（`/repos/:owner/:repo/contents/:path`）对于大文件会出现两类限制：
  - `content` 字段缺失/截断，或直接返回 **403**，提示该 API 只支持 1MB 以内内容。
- 当前 repoStore 读取逻辑在大文件场景仍可能失败（尤其在 Contents API 直接 403 的情况），需要引入 **Git Data API fallback**（走 `git/trees` + `git/blobs`）来稳定拉取 8MB 级别的文件内容。

## Proposed Changes

### A) 大文件加载兼容：repoStore.getFile 增加 Git Data API fallback（推荐主方案）

目标：
- 当报价 JSON > 1MB（乃至 8MB）时，依旧能稳定从 GitHub 拉取完整文件内容并 JSON.parse 成功。

修改文件：
- [github-sync/repoStore.js](file:///Users/jqz/Library/CloudStorage/OneDrive-%E4%B8%AA%E4%BA%BA/Github%20Project/minova/github-sync/repoStore.js)
- 同步修复 index.html 内联 repoStore（用于页面侧 GitHub 读写）：
  - [index.html:createRepoStore.getFile](file:///Users/jqz/Library/CloudStorage/OneDrive-%E4%B8%AA%E4%BA%BA/Github%20Project/minova/index.html#L2665-L2671)

实现细节（decision-complete）：
1. 在 `repoStore.getFile({ owner, repo, path, branch })` 中：
   - 先尝试 Contents API：
     - 成功且 `data.content` 存在：按现有逻辑解码。
     - 成功但 `data.content` 缺失且 `download_url` 存在：保留现有 download_url 路径作为次选（若失败继续 fallback）。
   - **若 Contents API 抛错且 status=403**（或返回体 message 包含 “blobs up to 1 MB”），执行 Git Data API fallback：
2. 新增 `getFileViaGitDataApi({ owner, repo, branch, path })`（在 repoStore 内部实现）：
   - `GET /repos/{owner}/{repo}/git/ref/heads/{branch}` → 得到 headSha
   - `GET /repos/{owner}/{repo}/git/commits/{headSha}` → 得到 treeSha
   - `GET /repos/{owner}/{repo}/git/trees/{treeSha}?recursive=1` → 找到目标 `path` 对应的 blob sha
   - `GET /repos/{owner}/{repo}/git/blobs/{blobSha}` → 得到 `content`（base64）+ `encoding`
   - base64 解码为 UTF-8 文本（见第 3 点）
3. 引入“安全 base64→UTF8 解码”（避免 `decodeURIComponent(escape(atob()))` 在大内容上不稳定）：
   - 使用 `atob` → `Uint8Array` → `TextDecoder('utf-8')` 的方式解码
   - 必要时按 chunk 解码（例如每 64KB 一段）以降低一次性内存峰值
4. 返回结构保持不变：`{ sha, content, raw }`（或 index.html 内联版 `{ sha, content }`），不改变上层 `readJsonFromGitHub()` 的调用方式与报价 schema。

### B) “新报价”清空：表格恢复到初始空白页 + 清空 Proposed System Size

目标：
- 用户选择“-- 新报价 --”并确认清空后：
  - 报价表格回到初次加载时的空白状态（1 行默认空行）
  - Proposed System Size 清空
  - 分割线状态与统计展示恢复一致

修改文件：
- [index.html:loadSavedQuote](file:///Users/jqz/Library/CloudStorage/OneDrive-%E4%B8%AA%E4%BA%BA/Github%20Project/minova/index.html#L9092-L9131)

实现细节：
1. 抽一个本地函数（位于 saved quotes 逻辑附近即可）：
   - `resetQuoteToInitial()`：构造与页面初次加载一致的默认 `quoteRows`：
     - `[{ id: Date.now(), description:'', vendor:'', spec:'', batchNo:'', quantity:1, price:0, cost:0, productId:'', inventoryId:'' }]`
     - 并将 `quoteSplit` 重置为 `{ enabled:false, afterRowId:null }`
2. 在 `if (!id) { ... }` 分支中：
   - 调用 `resetQuoteToInitial()` 而不是将 quoteRows 置空
   - 之后调用 `renderQuote()` + `updateQuoteSplitUI()`，确保表格 DOM 与分割线按钮状态同步
   - 清空 `#input-proposed-size`
3. 保持现有对 ROI/Part Breakdown/Reference/Site Overview 的内存态清空（partBreakdownData/referenceBlocks/roofBackground/pvModules）不变。

## Assumptions & Decisions

- 报价 JSON schema 维持现状（仍允许在 snapshot.memory 内保存 base64 图片）；本次以“更强的拉取/解码兼容”解决 8MB 加载失败。
- 不新增额外 UI 或弹窗；只修复加载与清空行为。
- 若未来希望进一步降低仓库体积/加载耗时，可追加二期：图片拆分为单独文件（assets）并在报价 JSON 内保存引用路径（本计划不做）。
